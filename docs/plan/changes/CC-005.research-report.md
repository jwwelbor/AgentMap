# CC-005 research report — recovery for non-text-only LLM responses

## Scope

CC-005 covers the non-streaming async receipt after a provider call succeeds
but contains no safe visible text. The affected contract is
`LLMResponse.text` and `LLMResponse.text_status`, returned by
`LLMService.call_llm_async()`. B005 deliberately keeps `text` a safe string
and marks a non-empty, textless response as `"non_text"`; it does not retain
the provider block list.

In this report, *block type* means a provider/LangChain content block's
`type` value only; *raw block* means the whole provider payload; and
*recovery* means a verified next action for the same logical request, not an
empty string that callers must guess how to handle. The scope excludes
streaming, raw reasoning exposure, provider billing changes, and a tool loop.

`docs/plan/changes/CC-005.md` is the authoritative change card. It requires
direct observation before AgentMap selects a recovery mechanism. The card does
not define a separate feature specification or test plan. This report records
the implemented observation capability and the evidence needed for the later
recovery decision; it does not authorize a retry, raw-block API, or streaming
change.

## Findings

1. **B005 correctly preserves a safe receipt state, but it does not provide a
   recovery channel.** `normalize_response_content()` admits only real text
   strings to `LLMResponse.text` and reports `"non_text"` for non-empty
   structured content without a usable text block. `_attempt_llm_call_async()`
   records success, usage, and cost, then constructs that receipt. The
   `LLMAgent` and fan-out paths preserve the status while retaining an empty
   text projection. The existing B005 tests cover the normalizer, real receipt
   path, agent entrypoint, and fan-out projection.

2. **The reported root cause is unobserved.** The card explicitly says that no
   failing production call has recorded its block-type list. Repository search
   finds no runtime `thinking` or reasoning configuration, and the Anthropic
   client factory passes only model, temperature, API key, optional token cap,
   and streaming usage. Therefore, a thinking-only result remains a plausible
   hypothesis, not a confirmed cause. Other valid block types, including tool
   use, remain possible.

3. **The upstream object still contains the information at AgentMap's
   boundary.** The locked `langchain-anthropic` 0.3.21 implementation keeps a
   non-text `content` list on `AIMessage`; for tool-use content it also derives
   normalized `tool_calls`. AgentMap receives that object, extracts normalized
   tool calls, and intentionally drops the rest when it creates its safe DTO.
   The SDK did not establish that the production occurrence is a thinking
   block; it only confirms that a content-free type diagnostic can be derived
   before AgentMap discards the list.

4. **Existing retry and telemetry mechanisms cannot safely answer the
   question.** A `non_text` response is a successful `LLMResponse`, so the
   exception-based resilience loop neither retries nor falls back. Retrying it
   automatically would create a second billed request and could duplicate a
   tool-producing turn. Existing response-content telemetry receives only
   `result.text` and emits nothing when it is empty, so enabling it cannot
   reveal the block type; logging raw blocks would violate B005's safety
   boundary.

5. **The streaming path is a separate contract.** It intentionally yields only
   `text_delta` events and ignores non-text deltas. Applying a non-streaming
   receipt recovery rule there would change terminal semantics and requires
   independent evidence.

## Decisions

1. **Observe before choosing a recovery mechanism.** This change adds a
   debug-level, content-free diagnostic immediately after
   `normalize_response_content()` returns `"non_text"` in
   `_attempt_llm_call_async()`. It records only provider, model, existing
   request identifier when available, finish reason, usage presence, block
   count, and an ordered list of block types. It does not log or return raw
   blocks, block text, thinking, tool arguments, IDs, or a provider-object
   representation. This extends `LLMService` receipt handling; it is not a
   raw-content API.

2. **Do not select raw-block exposure or automatic retry before direct
   evidence.** A raw `LLMResponse` field would cross B005's safety boundary
   into agent and fan-out consumers. An unconditional retry would treat a
   completed billable result as a failure and could repeat tool side effects.
   Neither is justified by the currently indirect token-count symptom.

3. **Choose the recovery only from the captured result.** If the diagnostic
   shows normalized tool use, the recovery is a consumer-owned tool-execution
   loop using `LLMResponse.tool_calls`, not a retry. If it shows a textless
   thinking, redacted-thinking, or another non-actionable block type, evaluate
   an explicit, opt-in one-call retry policy only after confirming that the
   request has no tools and that a second billed call is acceptable. If it
   shows a provider-specific non-actionable terminal result, return the
   explicit `non_text` receipt to the caller and create a narrowly scoped
   provider-contract follow-up. No observed result currently supports choosing
   among those outcomes.

4. **Verify the implemented diagnostic, then collect one real occurrence
   before implementing a recovery mechanism.**
   `test_cc005_non_text_receipt_logs_safe_block_type_diagnostic` drives
   `LLMService.call_llm_async()` through the client-factory seam, checks each
   safe diagnostic field, and proves that the provider payload is absent. The
   B005 agent and fan-out guards retain the safe receipt boundary. Enable
   debug-level logging for the next controlled failing production call and
   retain its safe metadata as the decision evidence. CC-005 remains limited
   to that observation capability until the captured block type supports a
   narrowly scoped recovery design.
