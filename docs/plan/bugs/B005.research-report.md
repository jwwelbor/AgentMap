# B005 research report — response text loss for non-text block lists

## Scope

B005 concerns the non-streaming async receipt path only: a provider has
already returned successfully, but `LLMResponse.text` becomes `""` when its
LangChain `content` is a list without a `{"type": "text"}` block. This is
observable through both `call_llm_async()` and `ask_async()`, whose public
convenience contract returns only that text string. The report does not change
code, provider configuration, billing, streaming, or the tool-execution loop.

Vocabulary: *response content* is the provider/LangChain block list;
*response text* is the text projection returned in `LLMResponse.text`;
*structured result* is a separately normalized result such as
`LLMResponse.tool_calls`; and *successful call* means `ainvoke()` returned
without raising, independently of whether a visible text block exists.

## Findings

1. **The reported behaviour is reproducible and is currently encoded as the
   expected contract.** `normalize_response_text()` filters list entries to
   dict blocks where `type == "text"`, then returns `""` if none match.
   `TestNormalizeResponseTextNoTextBlock.test_tc027_tool_use_only_yields_empty_string`
   and the live `LLMService` receipt test both assert that outcome. The focused
   test command passed on this branch, which proves the current tests preserve
   the loss rather than protect against it.

2. **The HTTP/provider success is recorded before the loss occurs.**
   `_attempt_llm_call_async()` awaits `ainvoke()`, then normalizes text,
   records circuit-breaker success, duration, provider response attributes,
   usage, and cost before building `LLMResponse`. A billed HTTP 200 with usage
   can therefore yield a successful receipt with `text == ""`; the debug log
   only reports response length zero.

3. **Tool-use is only partly preserved.** The same raw response feeds
   `extract_tool_calls(response)`, so LangChain-normalized `response.tool_calls`
   survives in `LLMResponse.tool_calls`. But callers of `ask_async()` receive
   only `response.text`, and any non-text block not duplicated into that
   normalized channel (for example a thinking/reasoning block) is absent from
   every `LLMResponse` field.

4. **The behaviour originated with related completed work, not a new service.**
   Commit `71f656f` (E05-F06, T-E05-F06-005) introduced both this exact rule
   and TC-027. Its stated purpose was to guarantee string text while handling
   tool blocks. T-E05-F06-006 subsequently supplied the send path for bound
   tools. B005 must therefore correct an existing receipt-normalization
   capability, rather than introduce a separate LLM path.

## Decisions

1. **Repair direction: extend the existing async receipt contract.**
   `LLMResponse.text_status` is a provider-neutral closed value:
   `"text"`, `"empty"`, or `"non_text"`. A non-empty block list with no
   text blocks produces `text == ""` and `text_status == "non_text"`.
   An empty string, an empty list, or text blocks whose combined text is empty
   produces `text_status == "empty"`. This preserves the safe string
   contract for `text` while making a successful non-text response visible to
   callers of `call_llm_async()`.

2. **Do not stringify arbitrary non-text blocks into `text`.** That would make
   tool arguments and potentially sensitive reasoning appear as user-visible
   answer text, lose a stable textual contract, and couple consumers to
   provider-specific representation.

3. **Add caller-path regression coverage.** Drive a successful mocked
   `ainvoke()` response containing only a `tool_use` block plus usage and
   finish metadata through `call_llm_async()`. Assert that the structured
   outcome is visible, `tool_calls` remains intact where provided, and
   success/usage/cost handling is unchanged. Also drive a `non_text` receipt
   through the production `LLMAgent.run_async()` entrypoint and the fan-out
   result projection. Never expose chain-of-thought content as application
   text.

4. **Scope boundary:** no change to provider billing, retries, fallback policy,
   tool dispatch, or `stream_seam.py` without a separately verified streaming
   contract. This is an extension of existing capability, not new work.

## Implementation evidence

- `normalize_response_content()` now derives the safe text projection and the
  receipt status in one pass. The unused `normalize_response_text()` wrapper
  was removed.
- `_attempt_llm_call_async()` stores the derived status on the successful
  `LLMResponse` after the existing success, telemetry, usage, and cost steps.
- The B005 caller-path regression calls `LLMService.call_llm_async()` through
  the real client-factory seam. It simulates a successful tool-use-only
  response and verifies `text_status == "non_text"` while normalized tool
  calls remain available.
- `ask_async()` remains a string-only convenience API. Callers that need to
  distinguish non-text content use `call_llm_async()` and inspect its receipt;
  the task does not introduce a raw-block projection or expose reasoning
  content.

Defect class: **receipt-state fields added but not consumed across receipt
consumers**.

The sweep inspected every production `LLMResponse` construction and every
production call or text projection associated with `call_llm_async()`:

| Surface | Count | Finding and disposition |
| --- | ---: | --- |
| `LLMResponse(...)` construction | 2 | `_attempt_llm_call_async()` creates the normalized status. The fallback handler's bare sync emergency wrapper bypasses the normalizer and is outside this async receipt contract; `LLMService` does not route production calls through that branch today. Its structured-content and status behavior is unverified and must not be inferred from this sweep. |
| `call_llm_async()` production call sites | 5 | Both `LLMAgent` branches now project `llm_response_status`; `ask_vision_async()` returns the full receipt unchanged; fan-out now copies `text_status`; `ask_async()` intentionally remains string-only. |
| Receipt `.text` projection locations | 7 | Agent and fan-out were fixed. Telemetry records only safe text. `ask_async()` is the documented scalar boundary. Three streaming fallback uses remain out of scope because `LLMStreamChunk` has a separate contract. |

Structural guards:

- `LLMAgent.run_async()` receives a successful `non_text` receipt and exposes
  `llm_response_status == "non_text"` while leaving output empty and omitting
  raw tool content.
- `call_llm_many_async()` receives the same receipt and preserves
  `LLMFanoutResult.text_status == "non_text"`.
- The receipt-normalizer tests cover `text`, `empty`, and `non_text` states.

## Structured content safety sweep

Defect class: **non-string provider response content shapes are unsafe when a
normalizer stringifies them into `LLMResponse.text`**.

The normalizer and its receipt/output projections were inspected as follows:

| Content branch | Result |
| --- | --- |
| Missing `content` attribute | Returns `("", "empty")`; the response object's representation is not exposed. |
| `str` content | Unchanged. Empty strings return `empty`; non-empty strings return `text`. |
| `list` content | Projects only `type == "text"` blocks. Lists without text blocks return `non_text`; empty lists return `empty`. |
| `dict` or other `Mapping` content | Returns `("", "non_text")` when non-empty and `("", "empty")` when empty. Raw mapping values are never stringified. |
| `None` or another non-list scalar | Returns `empty` for `None` and `non_text` otherwise. No non-string value is stringified. |

All seven previously enumerated receipt `.text` projections consume this safe
projection. The `LLMAgent` workflow-state and fan-out guards therefore keep a
structured payload out of agent output, memory, and fan-out text.

New guards cover a sensitive dict-shaped provider payload directly and through
`LLMService.call_llm_async()`: the text projection is empty, the receipt state
is `non_text`, and the payload secret does not occur in text.
