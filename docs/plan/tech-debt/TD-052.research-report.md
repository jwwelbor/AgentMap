# TD-052 research report — reproducible mypy and no-growth ratchet

## Scope

TD-052 covers the repository source check uv run mypy src, the configuration
and environment needed to make that check reproducible, and a CI policy that
prevents new diagnostics while existing errors are reduced. The eventual
acceptance target is a required, zero-error source check. Tests are outside the
target command, which selects src only. This debt concerns static analysis and
delivery controls; it does not establish a runtime defect or attribute
existing findings to B005.

For this report, a diagnostic is one mypy finding; a baseline is a versioned,
machine-readable set of diagnostics captured after configuration and tool
versions are fixed; and a no-growth ratchet rejects new diagnostic signatures
while allowing reviewed reductions. The canonical entity path is
docs/plan/tech-debt/TD-052.md. That file is absent from this dispatched
worktree, so the scope was checked against the shared project checkout and
the read-only Shark entity record. This report is written at the requested
sibling path.

## Findings

1. **The current command is nonzero and its configuration is malformed.**
   At commit 13ee240af10329b09ade001a35cf17741383c8a2, with CPython 3.11.14
   and mypy 1.19.1 from uv.lock, uv run mypy src reported 1,675 errors in
   253 files while checking 450 source files. It also reported a parse error
   in mypy.ini; the multiline exclude value closes at column one on line 65.
   Therefore this diagnostic count is a current failure snapshot, not an
   accepted baseline: mypy reported findings while also warning that the
   intended configuration could not be parsed.
   Representative findings include missing attributes in
   src/agentmap/services/registry_queries.py and
   src/agentmap/builtin_definition_constants.py, plus missing function
   annotations in src/agentmap/deployment/http/api/server.py.

2. **Two competing configurations exist, and they are not merged.**
   mypy.ini contains the detailed global and module-specific settings;
   pyproject.toml also defines [tool.mypy] with a smaller, different option
   set. Mypy searches mypy.ini before pyproject.toml and does not merge
   configuration files. The default command therefore selects the malformed
   mypy.ini; the pyproject settings do not repair it. The existing remediation
   plan correctly puts configuration repair before baseline capture.

3. **Developer, pre-commit, and CI entry points do not share one check.**
   Makefile's type-check target runs mypy on src through uv. The pre-commit
   configuration runs a separate mypy mirror pinned to 1.8.0 with an explicit
   mypy.ini; uv.lock resolves mypy 1.19.1. The CI workflow runs tests, Black,
   and isort, but does not run mypy or pre-commit. There is currently no hosted
   no-growth ratchet or required zero-error mypy gate.

4. **Historical counts are not comparable baselines.** B005 QA recorded
   1,613 errors across 248 files; the September remediation plan recorded
   1,644 across 249; the October S010/B102 artifact recorded 1,642 at base
   dc997387206552533b586c337add8d1b938676c7; and the current malformed-config
   run reports 1,675 across 253. The October baseline log also begins with a
   mypy.ini parse error. These snapshots differ by commit and configuration
   validity. The comparison artifact contains added/removed diagnostic
   messages, including import-stub changes, but it is not an enforced,
   current baseline. Counts alone cannot distinguish a true repair from a
   shifted, replaced, or dependency-induced diagnostic.

5. **The existing remediation is still the right capability to extend.**
   dev-artifacts/2026-09-11-mypy-remediation/plan.md already specifies the
   sequence: repair and reconcile configuration; capture environment,
   commit, error-code, and file-level evidence; add a no-growth CI check;
   reduce findings in dependency order without blanket suppression; then
   replace the ratchet with a required zero-error check. This report found no
   reason to replace that plan. Its historical counts must be refreshed after
   configuration is valid.

6. **The problem crosses configuration, dependency, source, and CI
   boundaries.** Mypy follows the source import graph, so dependency and stub
   changes can alter findings beyond the directly edited file. The
   uv.lock-backed mypy 1.19.1 run and isolated pre-commit mypy 1.8.0 run can
   produce different diagnostic sets. A count-only CI threshold can miss new
   findings when old ones disappear at the same time. Broad ignores, broad
   excludes, or reduced import following would make the check appear healthier
   without resolving the recorded debt and would weaken the intended contract.

## Decisions

1. **Extend the existing remediation plan.** Fix the mypy.ini parse error
   and choose one authoritative configuration before recording any baseline.
   Reconcile or remove the duplicate [tool.mypy] settings deliberately;
   do not assume both files contribute settings.

2. **Pin one execution environment for every accepted result.** Use the
   uv.lock-resolved mypy version and the same Python version, configuration,
   target, and dependency set in local and hosted checks. Align the pre-commit
   hook with that runner or treat it as advisory rather than baseline
   evidence. The hosted workflow should explicitly run the canonical
   uv run mypy src command after a locked dependency sync.

3. **Capture a fresh baseline only after configuration validation.** Record
   the base commit, Python and mypy versions, lockfile identity, exact command,
   full command output, counts by error code and file, and a sorted diagnostic
   multiset keyed by repo-relative file, error code, and normalized message.
   Keep multiplicity so a repeated finding in one file cannot be hidden by
   deduplication. The current 1,675 count and prior 1,613–1,644 counts are not
   candidates for the accepted baseline.

4. **Fail CI on newly introduced diagnostic signatures.** Compare candidate
   diagnostics with the checked-in baseline, reject additions even if the
   total count stays flat, and allow only reviewed reductions. Require an
   explicit review to update the baseline. Do not use broad ignore_errors,
   broad excludes, or a more permissive follow-import setting to shrink it.

5. **Reduce the backlog in dependency order, then close the ratchet.** Keep
   the existing plan's sequence from shared models, protocols, and result
   types through registry/configuration/storage, LLM/graph, and DI/runtime
   boundaries. Preserve B005's receipt contract. Replace the ratchet with a
   required uv run mypy src CI check only when the configured command
   returns zero errors.

6. **Reject the count-only and suppression alternatives.** A fixed error
   count can conceal replacement diagnostics; global suppression or skipped
   imports weakens the type-check contract. Requiring zero errors before any
   ratchet exists would leave the current large backlog without an actionable
   merge policy. A signature-based ratchet followed by zero-error enforcement
   matches the existing remediation goal and preserves incremental progress.
